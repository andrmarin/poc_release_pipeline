# Issues log

Every notable issue faced while building and operating this pipeline, and how it was
solved — kept so the same lesson never has to be learned twice. Ordered roughly
chronologically. Add a row whenever something bites; PR numbers refer to this repository.

| Issue | What is affected | How it was solved |
|---|---|---|
| Manually pushed SemVer tags would reintroduce typo/duplicate-version risk, conflicting with the "minimize human error" goal | Release strategy | The workflow computes the version and creates the tag itself; humans only approve releases, never name them (PLAN §2) |
| Production could only build `main` HEAD, so a hotfix would drag along unreleased features | Branching strategy, `release.yml` | Hotfix lane: branch from the **last production tag**, dispatch the release from `hotfix/*` (allowed by guard + deployment policies), forward-merge the PR afterwards |
| GitHub Actions app is rejected as a tag-ruleset bypass actor on user-owned repos (HTTP 422) | Tag protection, `setup-github.sh` | Automatic fallback: block tag update/deletion only (creation stays open on personal repos); the script converges to full lockdown when re-run on an org-owned repo |
| On the Windows dev machine `python3` resolves to the Microsoft Store stub and Git Bash has no `zip` | Local runs of `build.sh` / `verify.sh` | Scripts probe for a *working* interpreter (`python -c 'import zipfile'`) and fall back `zip` → Python for archive operations |
| A solo developer cannot satisfy the PR-approval requirement (cannot approve own PRs) | Branch ruleset, day-to-day flow | Admin bypass in **pull_request-only** mode: an admin can merge a PR without approvals but still cannot push to `main` directly; to be removed once the team grows |
| `prevent_self_review` left solo-dispatched production releases stuck on "Waiting for review" forever | Production environment gate | `setup-github.sh --allow-self-review` keeps the gate but allows self-approval; later `--no-approval` to remove the gate entirely for sandbox use |
| `gh release create` is not atomic: a failed asset upload leaves a published release and a tag the ruleset blocks from cleanup | `publish` job | Draft-first publish: create a *draft* (no tag, not public) → verify assets → publish as the final smallest step; a failure handler deletes leftover drafts (PR #11) |
| Releases page ordered `v...13` below `v...9` — GitHub compares tag names as **strings**, not dates | Versioning, Releases page | Run numbers zero-padded to 4 digits (`v2026.06.12.0045`) so string order equals chronological order (PR #13); existing tags migrated to padded names |
| Tag migration recreate failed: a `gh` token without the `workflow` scope cannot create tags via the releases API when commits contain workflow files — releases were temporarily lost | Release tooling, `gh` auth | Assets recovered **byte-identical** from the runs' Actions artifacts, tags pushed via git over SSH (no scope issue), releases recreated with `--verify-tag`; fix: `gh auth refresh -s workflow` |
| "Draft release for vX not found": the list-releases endpoint did not return a just-created draft, failing two production runs mid-publish | `publish` job | Stop searching by name — capture the release **id** from the create response and operate by id only (`GET`/`PATCH`/`DELETE /releases/{id}`) (PR #17) |
| One-off `403 Resource not accessible by integration` on draft creation (run #25) | `publish` job | Determined transient by an identical retest that ran green; guidance: dispatch a fresh run, don't re-run |
| Actions list showed bare "Release" entries — no hint which environment a run targeted | Run observability | `run-name: "Release: <environment> @ <branch>"` (PR #6) |
| Negative paths were untestable without throwaway branches; the first drill sabotaged the *previous* step; the raw failure message was cryptic | Failure testing (`SIM_FAIL_*`) | Repository-variable toggles (`SIM_FAIL_UPLOAD`, PR #12); failure moved *into* the upload step via a sentinel path (PR #14); sentinel path spells out the disarm command + error annotation + run-summary box (PR #18); production dispatches refused while armed |
| Re-running an old failed run reuses its frozen run number → a stale, *lower* version; a production re-run would even steal the **Latest** marker | Versioning integrity | Monotonic version guard: the computed version must sort strictly above the newest `v*` tag (PR #23). Caveat: runs created before the guard keep their old snapshot — don't re-run them |
| Squash-only merging rewrites commits, so the unmerged-hotfix guard (ancestor check) would deadlock every regular release after the first hotfix | `release.yml` guard, hotfix flow | Guard is squash-aware: a tag whose commit belongs to a PR merged into `main` passes (PR #24) |
| Merging a hotfix PR before releasing auto-deletes the branch (delete-branch-on-merge) — nothing left to dispatch from | Hotfix procedure | HOW_TO_RELEASE mandates the order: **release from the branch first, merge after** (PR #24) |
| Run durations looked alarming (e.g. "5m 0s" for ~30s of work) because GitHub includes approval-wait time and offers no way to exclude it | Run observability | "⏱ Pipeline duration" table written to the run summary: actual execution vs wall clock vs waiting (PR #25) |
| Artifact downloads were all named `sample-app-<env>.zip` — collisions in Downloads, no hint which is newest; staging ZIPs were double-suffixed (`...-staging-staging.zip`) | Actions artifacts | Artifact container named after the versioned ZIP that `build.sh` produced (single source of truth) — unique and chronologically sortable; the env suffix is skipped when the version already carries one (PR #26) |
| Staging/production badges often rendered "Unable to select next GitHub token from pool" — shields.io's shared GitHub-API token pool exhausts on their public instance | README badges | Shields.io dropped for dynamic badges: `scripts/badge.sh` renders SVGs, the release workflow's badge job publishes them (seeded by `setup-github.sh`), README serves them from raw.githubusercontent.com (PR #34) |
| Badge updates on a `badges` branch made GitHub show the "badges had recent pushes — Compare & pull request" banner on the repo home page; no setting disables it | Repo home page UX | Badge storage moved from a branch to a force-updated `badges` **tag** (parentless commits, lease-protected against races) — tag pushes don't trigger the banner, and raw.githubusercontent.com serves tags at the same URL (PR #35) |
